# Windsight — day-ahead wind forecast accuracy for GB power procurement

A web application for a UK electricity utility's day-ahead procurement desk. It
shows the wind generation forecasts that were **actually available when the
purchase decision had to be made**, and measures how far off they turned out to
be — using Elexon BMRS open data only.

- **Live application:** <https://qv7mzx.vercel.app>
- **API documentation:** <https://qv7mzx.vercel.app/api/docs> (OpenAPI 3, generated by FastAPI)
- **Repository:** <https://github.com/Ranjithsingh2004/qv7mzx>

## The problem

A GB utility buys power on the day-ahead market to serve its customers. How
much conventional generation it needs depends on how much wind there will be —
and wind is weather-dependent, so the desk has to commit on the basis of a
**forecast**, before gate closure on the day before delivery.

Two questions follow, and this product answers both:

1. **What did we actually know at the moment of the decision?**
2. **How wrong was that, quantitatively, so we can allow for it?**

The second question is easy to answer badly. Forecasts are revised
continuously, and some revisions land *after* the decision was made. Comparing
outturn against the latest available forecast measures hindsight, not the
decision. Windsight compares against the forecast that existed at an explicit,
configurable cutoff.

## What it does

- **Overview** — headline accuracy, the decision rule in force, data
  availability and coverage, and the source status.
- **Forecast versus actual** — an interactive hourly time series of the
  day-ahead forecast against measured outturn, with zoom, per-day filtering,
  and a **vintage inspector** that shows every forecast publication for a
  single hour and which ones the cutoff excluded.
- **Forecast accuracy** — MAE, RMSE, bias, error spread, MAPE, wMAPE and
  correlation, each with its definition available in the UI; an MSE
  decomposition separating systematic bias from random dispersion; and a
  **cutoff comparison** that re-runs the analysis at several deadlines.
- **Error analysis** — signed error through the window, and bias grouped by
  forecast lead time, by hour of the delivery day, and by delivery day.
- **Settlement period detail** — every analysed hour with its forecast, the
  publication time behind it, the outturn and the error; filterable, paginated,
  and exportable to CSV from the API.
- **Decision context** — how to read the numbers operationally, an explicit
  statement of what this dataset cannot support, and an optional
  residual-demand scenario driven by a demand figure the user supplies.
- **Data & method** — sources, the exact queries issued, normalisation counts,
  the vintage-selection rule step by step, and every assumption.

Light and dark themes, responsive down to phone width, keyboard navigable,
with a table equivalent behind every chart.

## Why the decision cutoff is the hard part

For each target hour, Windsight:

1. gathers every `WINDFOR` publication for that hour,
2. **discards any published after the decision cutoff**,
3. takes the most recent of what remains,
4. matches it to the `FUELHH` wind outturn for the same hour.

If nothing survives step 2 the hour is recorded as `no_eligible_forecast` and
contributes to no metric. It is never backfilled with a later forecast.

The **vintage inspector** in the UI renders this for a single hour — the
eligible publications, the excluded ones, and the one selected — so the rule
can be checked rather than taken on trust.

The default cutoff is **09:00 `Europe/London` on D−1**. GB day-ahead auctions
close mid-morning on D−1, so this sits ahead of gate closure. **It is a
documented product assumption, not a confirmed market rule**, and it is
configurable in the UI and the API.

## What January 2026 shows

Decisions 1–31 January 2026 (delivery 2 January – 1 February), 09:00 London
D−1 cutoff. 744 target hours, **100% matched**, 1,488 settlement periods, 280
forecast vintages retrieved.

| Metric | Value |
|---|---|
| MAE | 2,038.9 MW |
| RMSE | 2,504.8 MW |
| Mean bias (forecast − actual) | **+1,747.9 MW** |
| Error spread (SD) | 1,794.1 MW |
| Share of MSE from systematic bias | 48.7% |
| wMAPE | 18.07% |
| MAPE (actuals above 100 MW) | 22.04% |
| Correlation | 0.931 |
| Hours over / under forecast | 632 / 112 |

Two readings matter operationally:

- **The forecast tracks the shape of the day well but sits high.** Correlation
  is 0.931, yet 632 of 744 hours were over-forecast and 27 of 31 delivery days
  had a positive mean bias. Nearly half the squared error is a *stable offset*
  rather than noise — and an offset can be corrected for in advance, where
  dispersion has to be hedged.
- **Deciding later is worth a measurable amount.** Moving the cutoff from 06:00
  to 23:00 on D−1 takes MAE from 2,016 MW to 1,825 MW.

**Important caveat:** Elexon does not document `FUELHH` wind outturn and the
`WINDFOR` forecast as covering an identical set of wind assets. Part of that
+1,748 MW bias may therefore be a **scope difference between the two series**
rather than forecaster error. This cannot be resolved from the two datasets the
brief permits. The figures are reported as measured, the caveat is shown in the
product beside them, and the bias/dispersion split is provided precisely so a
reader can see how much of the headline depends on it. See
[`docs/METHODOLOGY.md`](docs/METHODOLOGY.md).

## Architecture and data flow

```
                    ┌──────────────────────────────────────┐
  Elexon BMRS       │  FastAPI backend (Python)            │
  Insights API      │                                      │
  ┌──────────────┐  │  elexon/client.py                    │
  │ FUELHH       │──┼─▶ async HTTP, timeouts, retries      │
  │ fuelType=    │  │        │                             │
  │   WIND       │  │        ▼                             │
  │ (half-hourly)│  │  elexon/normalise.py                 │
  └──────────────┘  │   WIND filter, validation,           │
                    │   duplicate/revision resolution      │
  ┌──────────────┐  │        │                             │
  │ WINDFOR      │──┼─▶      ▼                             │
  │ (hourly,     │  │  analysis/vintage.py                 │
  │  many        │  │   cutoff policy + vintage selection  │
  │  vintages)   │  │        │                             │
  └──────────────┘  │        ▼                             │
                    │  analysis/align.py                   │
                    │   half-hourly actuals → hourly grid  │
                    │        │                             │
                    │        ▼                             │
                    │  analysis/metrics.py                 │
                    │   MAE / RMSE / bias / MAPE / wMAPE   │
                    │        │                             │
                    │        ▼                             │
                    │  analysis/pipeline.py → service.py   │
                    │   orchestration + TTL cache          │
                    │        │                             │
                    │        ▼                             │
                    │  main.py — HTTP routes only          │
                    └────────┬─────────────────────────────┘
                             │ JSON over /api/*
                             ▼
                    ┌──────────────────────────────────────┐
                    │  React + TypeScript frontend          │
                    │  api/client.ts → hooks → sections     │
                    │  Recharts, design tokens, a11y tables │
                    └──────────────────────────────────────┘
```

Two deliberate boundaries:

- **HTTP does no data work.** `main.py` validates query parameters, delegates
  to the service, and serialises. Every analysis function is pure and
  synchronous, which is why the whole pipeline is testable from fixtures with
  no network.
- **The browser only ever talks to one origin.** The frontend calls a relative
  `/api` path. Vite proxies it in development, nginx proxies it in Docker, and
  the platform rewrites it in production — so there is no hard-coded backend
  host and no CORS preflight.

## Running it with Docker Compose

```bash
docker compose up --build
```

Then open:

| | URL |
|---|---|
| Dashboard | <http://localhost:8080> |
| API | <http://localhost:8000/api/health> |
| API docs (OpenAPI) | <http://localhost:8000/api/docs> |

nginx serves the built frontend on 8080 and forwards `/api` to the backend
container, so the browser sees a single origin. The backend is also published
on 8000 so the API can be opened directly during review. The frontend waits for
the backend's health check before starting.

```bash
docker compose down          # stop
docker compose logs -f backend
```

<details>
<summary>Building behind a TLS-inspecting corporate proxy</summary>

If your network presents its own certificate, package installs inside the build
will fail certificate verification. Point `EXTRA_CA_CERT` at a PEM bundle:

```bash
EXTRA_CA_CERT=/path/to/ca-bundle.crt docker compose build
```

Both Dockerfiles mount it as a build secret — so it never lands in an image
layer — and ignore it when it is absent, which is the default.
</details>

## Data sources and fields

Both are public Elexon BMRS Insights API datasets.

**Actual generation — [`FUELHH`](https://bmrs.elexon.co.uk/api-documentation/endpoint/datasets/FUELHH/stream)**,
filtered to `fuelType=WIND`. Half-hourly; `generation` is average MW over the
settlement period. Fields used: `startTime`, `settlementDate`,
`settlementPeriod`, `fuelType`, `generation`, `publishTime`.

**Forecast generation — [`WINDFOR`](https://bmrs.elexon.co.uk/api-documentation/endpoint/datasets/WINDFOR/stream)**.
Hourly; each publication is a *vintage* covering roughly 73 hours of target
periods. Fields used: `startTime`, `publishTime`, `generation`.

Behaviour confirmed against the live API rather than assumed: the `/stream`
endpoints return a bare JSON array with no pagination, so a month is a single
request; `FUELHH` rejects settlement-date and publish-date filters used
together; `WINDFOR` publishes about eight vintages a day but **not on a
guaranteed schedule** — January 2026 contains an off-schedule publication at
`2026-01-15T12:25:00Z`.

## Forecast-vintage selection

```
cutoff(D) = cutoff_time, Europe/London, on day D − cutoff_days_before
```

For each target hour on delivery day *D*: take every `WINDFOR` value for that
hour, drop those with `publishTime > cutoff(D)` (the comparison is inclusive —
a forecast published exactly at the deadline was available), and keep the
latest of the rest. Vintages are never merged or averaged. If none qualifies
the hour is `no_eligible_forecast`, reported separately from
`no_forecast_published`, because the two mean different things.

## Metric definitions

Computed from **matched hours only**; unmatched hours are counted and shown,
never treated as zero error.

**Sign convention: `error = forecast − actual`.** Positive means wind was
over-forecast, so the desk would have under-procured.

| Metric | Definition |
|---|---|
| MAE | `mean(\|error\|)` |
| RMSE | `sqrt(mean(error²))` |
| Bias | `mean(error)` |
| Error SD | standard deviation of error about its mean |
| Bias share of MSE | `bias² / MSE` |
| MAPE | `mean(\|error\| / actual)` over hours above the MAPE floor |
| wMAPE | `sum(\|error\|) / sum(actual)` |
| Normalised MAE | MAE ÷ mean actual |
| Correlation | Pearson *r* |

MAPE is undefined at zero and unstable near it, so it is restricted by the MAPE
floor and the included/excluded counts are always reported; **wMAPE** is given
alongside because it is defined for every matched hour. Undefined values are
returned as `null`, never zero — zero would read as a perfect forecast.
`MSE = bias² + variance` exactly, which is what makes the systematic/random
split meaningful.

## Timezones and daylight saving

- Every timestamp crossing a module boundary is timezone-aware **UTC**; naive
  datetimes are rejected rather than assumed.
- A **delivery day** is a `Europe/London` calendar day, because that is what a
  GB settlement date means. Day boundaries are computed in London and converted
  to UTC.
- London days are 23, 24 or 25 hours long across clock changes — 46, 48 or 50
  settlement periods. The analysis iterates UTC hours between London-resolved
  boundaries, so transition days come out correct rather than padded to 24.
  There are tests for both 2026 transitions.
- The cutoff is a *wall-clock* London time, so it tracks BST: 09:00 London is
  09:00 UTC in January and 08:00 UTC in July.
- The API returns both the UTC instant and a pre-rendered London string, so the
  frontend never re-derives a timezone and cannot disagree with the backend
  about a boundary. Every displayed time is labelled.

## Data quality and error handling

- Unparseable rows are **dropped and counted**, never coerced to zero, so bad
  upstream data reduces visible coverage instead of silently biasing a metric.
  The counts appear in the Data & method section.
- The `WIND` filter is applied upstream *and* during normalisation; a row with
  no `fuelType` is dropped rather than assumed to be wind.
- Duplicate actuals for one settlement period are treated as revisions — the
  later `publishTime` wins. Duplicate `(publishTime, startTime)` forecast rows
  are collapsed; distinct vintages never are.
- Negative generation is kept: wind farms can legitimately net-consume.
- Upstream calls have explicit timeouts and retry transient failures (429, 5xx,
  timeouts, transport errors) with exponential backoff; a 4xx is not retried.
  Exhausted retries surface as `502` with the underlying reason.
- The UI has distinct loading, empty, error and partial-data states, and
  distinguishes an invalid-parameter error (fix the controls) from an upstream
  outage (retry). A failed refetch keeps the last good analysis on screen.
- **There is no synthetic or demo data path.** Every figure the product
  displays is computed from Elexon responses; the API declares this as
  `data_mode: "live_elexon"` and the UI shows it. If Elexon is unreachable the
  product says so and shows nothing rather than substituting anything.

## Deployment

Deployed to Vercel at **<https://qv7mzx.vercel.app>**, as a **single project**
serving both halves:

- the React bundle is built by `buildCommand` and served as static assets;
- the FastAPI application runs as a Python serverless function via
  `api/index.py`, which imports `backend/app` so the identical code runs under
  uvicorn locally, in Docker, and on Vercel;
- `vercel.json` rewrites `/api/*` to the function and everything else to
  `index.html` for client-side routing.

Because both halves share an origin there is no CORS configuration and no
backend URL to configure in the frontend. No environment variables are set on
the deployment: the Elexon API is public, and every setting has a working
default.

## Known limitations

1. **Dataset scope cannot be reconciled.** `FUELHH` wind outturn and the
   `WINDFOR` forecast are not documented as covering an identical set of wind
   assets, so part of the measured bias may be a definitional difference rather
   than forecast error. The brief restricts this product to these two datasets,
   so it cannot be decomposed here. It is stated in the UI next to the figures.
2. **The decision cutoff is an assumption.** 09:00 London on D−1 is documented
   and configurable, not a verified market rule.
3. **Resolution mismatch is resolved by a choice.** Hourly forecasts against
   half-hourly actuals requires a reduction; two are offered and the headline
   moves by under 1% between them, but it is still a modelling decision.
4. **No demand, price or cost.** Out of scope for this engagement, so no procurement
   recommendation is produced. The residual-demand panel is explicitly driven
   by a user-supplied figure.
5. **Uncertainty bands assume normality.** Wind forecast errors are skewed and
   serially correlated; the scenario intervals are indicative width, not a
   calibrated risk measure. Labelled as such in the UI.
6. **Cache is per-process.** Fine for one container; on a serverless host each
   instance holds its own, so cold starts refetch.
7. **No authentication.** Appropriate for a pilot over public data; a
   production deployment would need access control.

## Future improvements

- Reconcile the coverage question with an additional outturn series and report
  skill against a like-for-like denominator.
- Bias correction as a first-class feature: fit the offset on a rolling window
  and report corrected alongside raw.
- Probabilistic intervals from the empirical error distribution per lead time,
  rather than a normal approximation.
- Persist analyses so month-on-month drift can be tracked without refetching.
- Portfolio view: apply national error to a user's own contracted position.
